# Proof Bundles

A separate app derived from Proof Protocol, with Solana transaction-pattern evidence and holder-verified Pro research. The original Proof Protocol app and repository are unchanged.

## New in 1.3

- Fresh token reports automatically run a free basic bundle scan; reopening a saved snapshot does not silently rescan.
- Bundle tech explains same-slot patterns, observed shared sources, transaction fees, declared priority prices, and why these do not establish a Jito bundle.
- Execution records preserve exact u64 priority prices and available zero-based block positions; older snapshots show “not collected” until refreshed.
- Mainnet RPC endpoints are checked against the Solana mainnet genesis hash before native evidence or holder reads.
- A Vercel adapter serves the app at `/bundles/` in the existing repository deployment. Browser mint and balance reads use the same-origin server gateway.
- Optional shared Redis REST storage supports one-use login nonces, sessions, protected report IDs and rate limits across instances. Pro fails closed on serverless hosts without shared storage; free scans remain usable.

## New in 1.2: our own launch engine

Gatekept is **not required** for the primary Pro feature. The native engine reads Solana RPC directly and does not call a third-party bundle-analysis API.

- Verifies the exact mint-initialization transaction; never infers creation from pool age or current holders.
- Automatic discovery is bounded to two pages of 1,000 mint signatures and four oldest candidate transactions. For older or active tokens, provide the creation signature. Failure to locate creation returns no launch verdict.
- Reads produced blocks in a five-slot initialization window. Missing blocks, unknown slot enumeration, an unfinished window, unavailable metadata and transaction truncation are reported explicitly.
- Analyzes up to 240 matching mint transactions. Same-slot signer-owned acquisitions remain patterns, not confirmed Jito bundles.
- Separates observed positive acquisitions, net changes inside the read window and later current balances. It does not invent an initial supply-allocation percentage.
- Checks current balances for up to six observed recipients and a small pre-acquisition SOL funding lookback for up to three. Unchecked or failed balances remain unknown. Shared funding sources do not establish identity.
- Protected JSON/CSV exports are generated by the server after another holder check.

The engine has a bounded read budget. Full-chain launch watching, complete root-funder tracing, cross-launch identity clustering, and continuous indexing are not implemented by this bounded engine. Reliable archival coverage still requires a suitable RPC provider or infrastructure operated by the owner. Paying for a competitor’s analysis service is optional.

## New in 1.1

- Coverage-first verdicts distinguish unavailable evidence from observed patterns. A 100% transaction fetch rate still does not establish complete launch coverage.
- Interactive recipient map: select a wallet to filter its exact transaction proof. Lines indicate observed slot associations, not transfers or common ownership. The same data is available in a searchable table.
- Pattern-slot timeline, integer-safe token formatting and labels that distinguish observed positive gains from current holdings.
- Up to 40 basic bundle snapshots in this browser, with historical deep links, deletion and whole-library JSON backups. Native and legacy Pro reports remain session-bound and server-protected.
- Compare the current sample with an earlier snapshot. Comparisons explicitly distinguish a shared anchor from different rolling windows and do not claim a change in overall bundle status.
- Stop waiting for a scan without saving an abandoned response. Upstream work may still finish and be cached.
- Three-step holder UI: wallet identified, ownership verified and holding checked. Existing sessions are refreshed on the holder page; no automatic message signing.
- Invalid wallet challenges return a clear client error. Rate limits include `Retry-After` and a retry interval.

Historical snapshots are local to the browser that captured them. Opening a snapshot link elsewhere does not fetch or invent that archived evidence. A new scan is required for current data.

## Run

Node.js 22 or later:

```sh
npm ci --ignore-scripts
npm start
```

Open http://127.0.0.1:3000. Original token search, Proof scores, saved reports, watchlist and wallet connection are retained. Basic sampled scans are free by default. Verified holders unlock deeper launch scans and CSV/JSON launch exports.

The selected policy is `free-basic`. To set it explicitly, run:

```sh
BUNDLE_ACCESS_MODE=free-basic npm start
```

Basic sampled bundle checks need no wallet. Native Pro launch reports and their CSV/JSON exports require server-verified holder access. Existing Proof score exports remain free; a client can always copy public data, so frontend button hiding is not treated as access security.

## Configuration

Set these in the deployment host's environment settings. `.env.example` lists the names. Do not commit secrets or paste private keys into the app.

| Variable | Required for | Value |
| --- | --- | --- |
| `APP_ORIGIN` | Browser API requests / login | Exact origin, e.g. `https://bundles.example.com`, no trailing slash. Defaults to `http://127.0.0.1:3000`. |
| `BUNDLE_ACCESS_MODE` | Bundle scans | `free-basic` (default, selected policy); `holders-only` is an optional operator override. |
| `HOLDER_TOKEN_MINT` | Holder Pro | The official Solana SPL mint, supplied by the owner. No mint is invented. |
| `HOLDER_MIN_TOKENS` | Holder Pro | Positive decimal number of tokens, supplied by the owner; converted using mainnet mint decimals. |
| `SOLANA_RPC_URL` | Mainnet transaction / holder data | A dedicated archival Solana mainnet HTTP RPC is recommended. Default: `https://api.mainnet-beta.solana.com` with public-node fallback. URLs containing API keys are secrets. |
| `GATEKEPT_API_KEY` | Optional legacy comparison only | Not needed for native Pro scans. An authorized key with credits enables only the explicitly called legacy `/api/bundles/indexed` adapter. |
| `STATE_REDIS_REST_URL` | Pro on serverless / multiple instances | HTTPS Redis REST endpoint supporting `GETDEL`, `SET EX`, and `EVAL` (e.g. Upstash). |
| `STATE_REDIS_REST_TOKEN` | Shared storage | Server-only REST access token; never expose in browser assets. |
| `NODE_ENV` | Production | `production`; requires HTTPS `APP_ORIGIN`. |
| `HOST` | Container/server binding | `0.0.0.0` in a container; local default `127.0.0.1`. |
| `PORT` | Server | Default `3000`. Match the public origin/proxy configuration. |

For local configuration, Node 22 can load an owner-created `.env` without another package:

```sh
node --env-file=.env scripts/serve.mjs
```

Do not put a private RPC URL or provider key into `dist/` or frontend localStorage. Config endpoints expose only the official mint, threshold and availability flags.

## What the basic bundle checker actually checks

- **Recent mode:** up to 12 successful transactions from the latest 60 signatures referencing the mint. Null, pruned and unavailable transactions remain explicit coverage gaps.
- **Anchor mode:** provide a transaction signature. The backend retrieves its block, selects up to 12 matching mint transactions, and inspects that slot. A mint-initialization label requires a parsed SPL initialization instruction for that exact mint in the anchor transaction. No full launch-history coverage is implied.
- A pattern requires at least **two distinct transactions and two distinct signer-owned recipients** with positive net raw token balance changes in one slot.
- Pool/vault owners that did not sign the transaction are excluded. Positive token changes are acquisitions, not necessarily buys.
- Shared SOL transfers are shown only when the sampled transactions contain transfers from one source to at least two pattern recipients. This is not root-funder tracing.
- Every recipient, transaction and slot is linked to Solscan. No same-slot result is labeled a confirmed Jito bundle or proof of common ownership.
- **No pattern in a limited sample does not establish an unbundled launch.** Current holder concentration does not establish historic bundle allocation.

Transactions and signatures are requested from Solana mainnet through the server. Public RPC nodes may throttle requests or lack archival history. A sample can be incomplete, and the UI says so. Sample reads are cached for 45 seconds and identical in-flight reads are deduplicated.

## Optional legacy provider comparison

The primary UI uses our native engine. A backwards-compatible, optional endpoint still uses the [documented GateKept API](https://gatekept.io/developers/docs):

```text
GET https://api.gatekept.io/api/v1/bundles/launches/{mint}
Authorization: Bearer <server-side key>
```

This returns **stored launches only**; it does not trigger new indexing. A 404 is displayed as **Launch not indexed**, never as a clean verdict. Provider attribution, launch allocation, bundle wallets, related launches and tracked supply still held remain labeled as provider records. Initial allocation and currently held supply are displayed separately.

The documented endpoint costs **5 credits per successful uncached read** (the docs estimate 1 credit ≈ USD 0.001). Reports are cached for 120 seconds. This implementation caps calls at 20 per hour **per server process** and limits protected requests per wallet. It does not buy credits or subscribe the owner to a plan. A real authorized API key and credits are still required to verify the live integration. The adapter is tested against the documented response shape; no live indexer access is claimed before setup.

## Holder access

1. Connecting Phantom or Solflare only reads the public address.
2. The visitor explicitly selects **Verify holder access**, reads a domain-bound login challenge, and signs that message. No transaction, approval or transfer is requested.
3. The server verifies Ed25519 ownership, consumes the two-minute nonce once and issues an HttpOnly, SameSite=Strict cookie. HTTPS production cookies are Secure.
4. Protected scans and exports require that session and **recheck token holdings on mainnet** using the exact configured mint and decimals. Client-provided wallet names or `pro: true` are ignored.
5. Sessions expire after ten minutes. Disconnect/logout revokes access. Unavailable RPC, invalid balances and insufficient holdings fail closed for Pro.

Threshold arithmetic and raw token balances use BigInt. Multiple owned token accounts are summed. Mint/owner mismatches are rejected. Frozen, delegated or protocol-owned balances are not a promise of economic ownership beyond the RPC's token-account owner field.

With `STATE_REDIS_REST_URL` and `STATE_REDIS_REST_TOKEN`, login nonces, sessions, report IDs and bundle API rate limits use shared TTL storage scoped to the application origin. Nonces are consumed atomically with `GETDEL`; every export still rechecks holdings. Without shared storage, standalone Node uses process-local state and is single-instance only; restarts require signing in again. Serverless hosts disable holder access without shared storage. Native read caches and scanner concurrency remain process-local. High traffic also needs provider capacity and platform-level abuse controls. Holder messages and access checks have automated cryptographic/API tests; an actual eligible holder wallet has not been verified without the owner's mint and threshold.

## API

| Endpoint | Access |
| --- | --- |
| `GET /api/config` | Public policy and integration availability |
| `POST /api/auth/challenge` | Domain-bound wallet challenge |
| `POST /api/auth/verify` | Verify signed message, issue session |
| `POST /api/auth/logout` | Revoke session |
| `GET /api/session` | Current session / fresh holder status |
| `POST /api/bundles/scan` | Policy-controlled basic RPC sample |
| `POST /api/bundles/launch` | Native engine · session + current holder balance |
| `POST /api/bundles/indexed` | Optional legacy provider comparison · session + current holder balance |
| `GET /api/bundles/export?id=…&format=json` | Holder-verified native or legacy report export |
| `GET /api/bundles/export?id=…&format=csv` | Holder-verified wallet export |

POST requests require the matching `Origin`. Provider errors are mapped to safe messages, and upstream secret URLs/headers are not returned. CSV exports come from server-held reports rather than client-supplied data.

## Checks

```sh
npm test
npm run check
```

Tests cover exact execution evidence, cross-instance login/nonce consumption/export/logout, shared storage failures, serverless access controls, the retained Proof score, grouping false positives, raw integer balances, verified mint initialization, bounded native discovery, partial launch windows, funding evidence, missing metadata, provider mismatches, signed-message replay/expiry, balance thresholds, API access, CSRF and protected exports. GitHub Actions installs locked dependencies and runs these checks.

## Deploy

This version requires a Node backend; uploading only `dist/` to a static host will not provide holder access or bundle endpoints. A Node container definition is included. Set the environment variables above on a host supporting Node 22, persistent process-local service and HTTPS. No deployment platform credentials are embedded.

This app is included in the existing `jaycarson373-tech/proof-protocol` repository at `apps/proof-bundles/`. Deploy with that folder as the service root (or Docker build context). The root `vercel.json` builds both apps and serves this app at `/bundles/` with a Node API function. For a standalone service, use this folder as its root and set an exact HTTPS `APP_ORIGIN`. No dedicated RPC, holder policy or Redis credentials are embedded. Saved reports and watchlists start empty in this app's separate `proofbundles.` browser namespace.
